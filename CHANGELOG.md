# Changelog

## Unreleased

- Every mounted peer has a stable sector IRI, and every call to it is recorded (ledger #4555, epic #4553). A `gonk.mount` line may end in `sector=<name>`, giving `urn:iki:gonk:sector:name:<name>`, or in `sector=<IRI>`. With neither, the sector is the peer's configured name: the last part of its certificate directory, or the stem of its socket's file name. It stays the same across restarts and certificate rotation. Nothing derives from it yet. Each call a mount sends its peer writes a `urn:iki:gonk:class:PeerCall` entry into the log segment, naming the peer, its sector, the verb, the outcome, the duration and the caller's principal. The startup banner and a failed dial's stderr line name the sector too.
  - **Upgrade:** the configuration only gains an optional word, so an older `gonk.mount` line loads unchanged and gets the default sector. Nothing persisted changes shape.
- The tables keyed by a client fingerprint (`clients.json`, the `clients/` directory, the grants a fingerprint reaches in `grants.json`, the participants graph, the onboarding fold) now carry the rule for that key in a comment: the key is one peer's view of a principal, to be treated as opaque. Never assume another peer sees the same string (ledger #4555). No behavior changes.

- Most-relevant-first ordering is no longer refused because the word index miscounted (ledger #4448, #4438). Through ikigai-store 0.6.3, a ledger's first index build could overlap writes and leave its index one document high. The ledger's completeness check then refused `sort=relevance` until a restart. gonk now requires ikigai-store 0.6.4, which fixes the count.
  - **Upgrade: every enrolled index rebuilds once on the first start.** 0.6.4 raises the index format from 1 (what ikigai-store 0.6.2 wrote) to 3, so the store discards each ledger's old index on open and rebuilds it from the store in the background. Nothing is lost: the index is derived. Measured on a debug build, the rebuild took 1.6 seconds for a ledger of 5,000 items (10,000 titles and bodies, bodies of about 1 KiB) and 13 seconds for 50,000 items. A release build is faster. While a ledger's index rebuilds, its searches still answer by scanning and the page says that most relevant ordering is not available. Most relevant ordering works again once the rebuild finishes. The rebuilt index takes about 370 bytes per item on disk.
- An item page lists the item's agent sessions (ledger #3024): an "Agent sessions" panel with one row per session summary the ledger holds for the item, newest first: session id, when it was recorded, machine, harness, model, exit status, wall-clock time, turns, and input, cached input, cache creation and output tokens. Read from the ledger's own `item:{id}:sessions` face under the viewer's grant; nothing is totaled or priced. A field the harness did not report reads "not reported", never 0; a session posted with no summary is not listed; an item with none has no panel; and a grant that does not reach the session graph reads the ledger's refusal as a sentence.
- A tenant can export its whole ledger graph, however large, under its own read grant (ledger #3649): `Source urn:iki:gonk:export:graph` with `graph=<iri>` streams every quad of that one named graph from one snapshot as N-Quads, a 64 KiB chunk at a time. Before, a tenant's scoped SPARQL read was refused past 100,000 quads or 16 MiB, and the store's dump needs the broad read no tenant may hold. The caller needs the read token for exactly that graph, which a ledger's Read, Audit, Worker, Write, Delete and Purge grants all hold. The raw-read rule applies at every door as it does to the store's scoped reads, and a call that rule narrows is streamed under the narrower grant rather than collected. The stream is cut into windows of at most 100,000 quads and 16 MiB, further bounded by the caller's answer grants, and each window must be produced within the caller's time budget. The streamed total has no ceiling beyond those per-window bounds: a 5,000,000-quad ledger is about 928 MiB. A window past a bound ends the stream with an error, so a failed export is never mistaken for a complete one. At most two exports read at once; a third is refused RetryAfter.
- The Layers page's unread cursors and feed subscriptions follow the person after the people upgrade (ledger #4436). Before people they were keyed by the passkey IRI, so after the upgrade every layer read as unread and the subscriptions were gone. A person now adopts the entries of every passkey that names it: the larger cursor per layer, and the union of the subscriptions. They are written under the person at the next save. The passkeys' entries stay for a downgrade, and what was adopted is recorded in `layers-view/cursors-adopted.json` and `layers-view/subscription-adopted.json`.

## 0.1.3

- Optional arguments now report invalid values that previously selected a default silently. Omitting an argument still selects its default. No stored data changes.
